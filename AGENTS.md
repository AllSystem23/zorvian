# Zorvian ERP — Project Memory

## Stack
- **Frontend**: Flutter 3.x · Riverpod · GoRouter · Material 3
- **Backend**: ASP.NET Core 9 · EF Core 9 · Clean Architecture · FluentValidation
- **Database**: PostgreSQL 16 (Neon) · Row-Level Security
- **Cache**: Redis 7 (RedisCacheService con IDistributedCache + auto-fallback a InMemoryCacheService)
- **Messaging**: SignalR (NotificationHub) · Hangfire (job scheduler) · **RabbitMQ 3.13 via MassTransit** (4 consumers activos)
- **Jobs**: Hangfire con persistencia PostgreSQL (15 jobs: 11 recurring + 4 ad-hoc)
- **Search/Logs**: Serilog (console + Elasticsearch condicional + file). Elasticsearch integrado via Serilog.Sinks.Elasticsearch
- **Auth**: Firebase Auth + JWT (1h access / 7d refresh). API Keys. MFA (backend + frontend UI)
- **Observability**: OpenTelemetry SDK (tracing + metrics + OTLP). Serilog (console + ES + file). Sentry (frontend). Prometheus/Grafana pendientes
- **AI/ML**: ML.NET · Vertex AI (ChatService) · RAG (EmbeddingService) · OCR (OcrService)
- **Infra**: Render.com · Firebase Hosting · CloudFlare · Docker
- **CI/CD**: GitHub Actions (1 workflow: ci-cd.yml, 5 jobs)
- **Testing**: xUnit y Moq (backend). Flutter test (frontend). K6 (load testing). 158 archivos de test backend (1344 tests) · 460 tests frontend

- **Widgets**: Design System (`ZCard`, `ZButton`, `ZStatCard`, `ZDataTable`, etc.) from `shared/ds/ds.dart`
- **ListTile dentro de ZCard**: `ZCard` pinta su fondo con un `DecoratedBox`; un `ListTile` con `onTap`/`onLongPress` (o `tileColor`) pinta sus ink splashes sobre el `Material` ancestro más cercano → sin un `Material` intermedio el splash queda oculto y Flutter lanza el assert *"ListTile background color or ink splashes may be invisible"* en debug. **Todo `ListTile` dentro de un `ZCard` va envuelto en `Material(type: MaterialType.transparency)`** (igual que `SwitchListTile`). Lo vigila `frontend/test/zcard_list_tile_drift_test.dart` (escanea `lib/**/*.dart` y falla si falta el `Material`).

## Vacaciones y permisos: saldo descontado + retenciones de RRHH (2026-10-16)
Tres brechas cerradas: (a) vacaciones descuentan saldo por las 3 vías de consumo, (b) permisos descuentan sus buckets al aprobar, (c) la nómina respeta `IsPaid` de los permisos. Migración `20261016200539_AddVacationPayrollRunAndPermissionHalfDay` (`VacationRequests.PaidByPayrollRunId` uuid null + índice; `PermissionRequests.IsHalfDay` bool default false).
- **(a) Vacaciones — fuente de verdad = solicitudes; `LeaveBalances` = espejo**: helper `LeaveBalanceSync.SyncAsync(repo, tenant, employeeId, year)` (`Zorvian.Application/Helpers/`) recalcula `VacationDaysTaken`/`VacationDaysPending` idempotente (SIN `+=`) en cada transición: crear, rechazar, `MarkTakenAsync`, pago por recibo RV, flip/revert de corrida. `VacationRepository.GetVacationBalanceSumsAsync(employeeId, year?)`: taken = solo `"taken"`; pending = `"pending"` + **`"approved"`** (las aprobadas ahora RESERVAN saldo — antes el saldo disponible quedaba sobreestimado); medida BusinessDays-preferente (`BusinessDays > 0 ? BusinessDays : TotalDays`); año por `StartDate`.
- **Estados**: `pending → approved → taken` con TRES vías a taken: (1) pago por recibo RV (`PayVacationAsync`), (2) **`PUT /zorvian/v1/vacations/{id}/mark-taken`** (`VacationService.MarkTakenAsync` — vacación descansada SIN recibo; solo desde `approved`, si no → 400 con el estado actual), (3) corrida de nómina aprobada (`PaidByPayrollRunId` marca la vía 3).
- **Ciclo de nómina**: `ApproveRunAsync` (dentro de `if (period != null)`) pasa a `"taken"` las `GetApprovedInRangeAsync(...)` y setea `PaidByPayrollRunId = run.Id`, con sync agrupado por EmployeeId+Year; `CancelRunAsync` revierte (`GetByPayrollRunAsync` → `approved` + `null` + sync). **Anti doble pago**: `PayVacationAsync` lanza si una corrida NO cancelada de un período que solapa las vacaciones existe ("corrida de nómina activa"); `GeneratePayrollAsync` lanza si el período ya tiene corrida no cancelada (hay que borrar el borrador o cancelar — cancelar reabre el período y revierte el consumo).

Fuente: `IPermissionRepository.GetApprovedOverlappingAsync(period.StartDate, period.EndDate)`; overlap medido en días hábiles (0.5 si half-day).

## Reactividad al cambio de empresa/sucursal en el header (2026-10)
Barrido completo del frontend. `branchScopeProvider` (`core/providers/company_branch_provider.dart`) es la key de invalidación `'${companyId}_${branchId}'`; el `DioClient` lee `companyBranchProvider` en cada request (headers `X-Tenant-Id` / `X-Branch-Id`), así que el backend siempre ve el scope nuevo.

  @override
  XState build() {
    final scope = ref.watch(branchScopeProvider);
    if (_lastScope != null && _lastScope != scope) {
      Future.microtask(() => load());

    _lastScope = scope;

## "El log de auditoría no se deja borrar" (2026-10-31) — AUD-004 vs. retención
Causa raíz del incidente: la inmutabilidad está implementada **dos veces** y había que abrir las dos. (1) En EF, `AuditImmutabilityInterceptor` rechaza **cualquier** `EntityState.Deleted` sobre `AuditLog` (AUD-004), así que `AuditLogCleanupJob` y la purga de mantenimiento morían en el `SaveChanges` con `InvalidOperationException`. (2) En PostgreSQL, el trigger `trg_audit_logs_immutable` → `audit_logs_block_mutation()` rechaza `UPDATE`/`DELETE`/**`TRUNCATE`** con `SQLSTATE P0001` (`AUD-004: AuditLogs es inmutable. Operación TRUNCATE sobre tabla AuditLogs está bloqueada...`) — el error literal que reportó el operador: ningún cambio de C# lo evita porque la sentencia ni llega a ejecutarse. La tabla de auditoría **nunca se purgaba** y crecía sin techo hasta llenar el proyecto de Neon. Los tests no lo veían por tres motivos: (a) usaban `UseInMemoryDatabase` **sin registrar interceptores** (falso verde), (b) el job viejo hacía `ToListAsync()` de todo y el borrado ni siquiera llegaba a intentarse en producción, y (c) la capa SQL (trigger) no se puede simular con InMemory. Estado al cierre: build 0/0, backend **1588/1588**, `has-pending-model-changes` limpio, `flutter analyze lib test` 0 issues, frontend **842/842**.
- **`AuditRetentionScope`** (`Infrastructure/Data/AuditRetentionScope.cs`): scope `AsyncLocal<int>` (`Begin()` / `IsActive`, anidable, se cierra solo en el `using`). Es la **única** excepción a AUD-004: con el scope activo el interceptor permite `Deleted`; `Modified` (alterar contenido o soft-delete) sigue prohibido **siempre**, también dentro del scope. Lo abren solo `AuditLogCleanupJob.RunAsync` y las purgas de `DatabaseMaintenanceService`. `AsyncLocal` porque los interceptores son singletons de DI y el borrado ocurre en jobs/contextos distintos.
- **`PurgeExpiredDataAsync` incluye `AuditLogs`** (6 meses) además de `DataRetentionRules.All`: si el operador lanzaba la purga para liberar espacio, la tabla más grande de logs quedaba intacta. `AuditLogs` sigue **fuera de `All`** para no duplicar la ventana de su job propio (el test `DataRetentionRules_NeverIncludeBusinessTables` lo exige). La purga por `ctid` en lotes no necesita el scope (SQL crudo), pero el camino EF/InMemory sí.
- **`TruncateRetentionTablesAsync`** (purga de EMERGENCIA): `TRUNCATE` de las tablas de retención. Con la base llena Neon devuelve `53100` **también al borrar** (un `DELETE` necesita páginas nuevas para las versiones muertas), y `TRUNCATE` crea el archivo vacío sin pedir espacio → es la única operación que desbloquea las escrituras desde el API. `ResolveTruncateTargets` (público, testeado) **ignora** cualquier nombre fuera de la whitelist (tablas de negocio incluidas) y lo reporta en `notes`; `AuditLogs` exige `includeAuditLogs=true`. Endpoint `POST zorvian/v1/system/db-storage/truncate?tables=&includeAuditLogs=` (CSV, `company.manage`, sin `[Audit]`).
- **Preflight de arranque** (`Program.cs` paso 0): `GetStorageReportAsync(5)` antes de migrar; si `IsStorageFull` → `LogCritical` y se omiten migraciones, Fleet SQL, seeders y `EnsureAccountsAndLinksAsync` (arranque degradado en vez del crash-loop `Exited with status 139`). `storageFull` se declara arriba y también se activa si un seeder choca con el 53100 (`SeedSafelyAsync`).
- **Payload de auditoría acotado** (`AuditInterceptor`): `MaxSerializedValueLength = 1000` + `ClampValue(...)` en `SerializeEntry` y en los diccionarios old/new del `Modified`. El snapshot guardaba el HTML completo de `DocumentVersion`/`DocumentTemplate` (40-80 KB **por fila**), que era otro consumidor silencioso del GB. Se recorta el **valor** (no el JSON completo) para que la fila siga siendo parseable.

DISABLE TRIGGER` para builds viejos y **1.b** `set_config('zorvian.audit_retention','on',true)` + `TRUNCATE`, cada uno dentro de `BEGIN/COMMIT`) y `docs/DB_STORAGE_RECOVERY.md` (secciones 1, 2.1, 3 y 4 ampliadas, con la nota de las dos capas de AUD-004).

- **Gotchas**: (1) `UseInMemoryDatabase` **sin** `.AddInterceptors(...)` no simula AUD-004: cualquier test de borrado de auditoría debe registrar el interceptor o pasa en falso. (2) `ExecuteDelete` no existe en InMemory → el camino no-Postgres usa `RemoveRange` + `SaveChanges` (de ahí la necesidad del scope). (3) `TRUNCATE` es transaccional: si el lote falla después, PostgreSQL deshace el vaciado; `VACUUM` no puede ir en el mismo lote. (4) `AuditLog` tiene `HasQueryFilter` por tenant → la purga global usa `IgnoreQueryFilters()`. (5) Moq: parámetros opcionales nuevos en interfaces exigen `It.IsAny<...>()` explícito (CS0854). (6) `flutter test` en Windows puede terminar con varios "did not complete" si quedan `flutter_tester` huérfanos o demasiados isolates: matar los procesos, borrar `build/native_assets` y repetir con `-j 4` (los mismos archivos pasan aislados). (7) `set_config` con `is_local = false` **envenena la conexión del pool** (el siguiente request borraría auditoría sin querer): siempre `true` y dentro de la transacción del borrado. (8) `BEFORE ... FOR EACH STATEMENT`: el `RETURN NULL` de la función se **ignora** (solo los triggers `FOR EACH ROW` pueden saltar la fila), el bloqueo lo produce el `RAISE EXCEPTION`; el escape con `RETURN NULL` es por tanto correcto y no "cancela de más". (9) El `REVOKE` deja `AuditLogs` solo-lectura para `zorvian_app`: si algún día la app se conecta con ese rol (reducción de privilegios pendiente), la retención debe correr con el **rol owner**. (10) Npgsql acepta varias sentencias en un `CommandText` solo si no hay parámetros → el `DELETE` por `ctid` (parametrizado) necesita transacción explícita, no un batch de sentencias.
- **Desbloqueo inmediato en Neon (sin deploy, build viejo)**: en la consola SQL, `BEGIN; ALTER TABLE "AuditLogs" DISABLE TRIGGER trg_audit_logs_immutable; TRUNCATE TABLE "AuditLogs"; ALTER TABLE "AuditLogs" ENABLE TRIGGER trg_audit_logs_immutable; COMMIT;` y después, en una ejecución aparte, `VACUUM (ANALYZE) "AuditLogs";`. Con la migración ya desplegada basta `BEGIN; SELECT set_config('zorvian.audit_retention','on',true); TRUNCATE TABLE "AuditLogs"; COMMIT;`. Nota: el `TRUNCATE` no baja el `pg_database_size` si hay otras tablas dominantes — es el `VACUUM FULL` (o dump/restore) el que devuelve el espacio.
